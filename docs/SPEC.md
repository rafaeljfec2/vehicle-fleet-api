# Fleet Management API — Functional Specification

## 1. Intent

Deliver a small Node.js/TypeScript REST API for vehicle fleet management: automobiles, drivers, and automobile usages. Persistence is in-memory. The solution must be testable, easy to run, and documented for a three-day technical assessment.

## 2. Domain models

### Automobile

| Field | Type | Rules |
|---|---|---|
| `id` | UUID v4 string | Generated by the server; client never sends it |
| `plate` | string | Required; trimmed; uppercased; unique; 1–10 chars; `^[A-Z0-9-]+$` |
| `color` | string | Required; trimmed; 1–60 chars |
| `brand` | string | Required; trimmed; 1–60 chars |

### Driver

| Field | Type | Rules |
|---|---|---|
| `id` | UUID v4 string | Generated by the server |
| `name` | string | Required; trimmed; 1–120 chars; not unique |

### Usage

| Field | Type | Rules |
|---|---|---|
| `id` | UUID v4 string | Generated by the server |
| `automobileId` | UUID v4 string | Must reference an existing automobile |
| `driverId` | UUID v4 string | Must reference an existing driver |
| `startDate` | ISO-8601 datetime | Required; must include time (date-only rejected) |
| `endDate` | ISO-8601 datetime or `null` | `null` means active; when set, `endDate >= startDate` |
| `reason` | string | Required; trimmed; 1–255 chars |

**Relationships:** a usage references one automobile and one driver. History of finished usages is retained. Listing joins current automobile and driver data (no snapshot).

## 3. Acceptance criteria

### Automobiles

| ID | Criterion |
|---|---|
| AC-A1 | Creating an automobile with valid `plate`, `color`, and `brand` returns `201` and a body that includes a generated `id`. |
| AC-A2 | Creating with missing or invalid fields returns `422` with per-field details. |
| AC-A3 | Creating with a plate that already exists (case-insensitive after normalization) returns `409`. |
| AC-A4 | Getting by existing `id` returns `200` and the automobile. |
| AC-A5 | Getting by well-formed UUID that does not exist returns `404`. |
| AC-A6 | Getting by malformed UUID returns `422`. |
| AC-A7 | Listing without filters returns all automobiles in insertion order. |
| AC-A8 | Listing with `brand` and/or `color` filters applies exact, case-insensitive match; both filters combine with AND. |
| AC-A9 | Updating with a full valid body replaces plate, color, and brand and returns `200`. |
| AC-A10 | Deleting an automobile with no usages returns `204`. |
| AC-A11 | Deleting an automobile referenced by any usage (active or finished) returns `409`. |

### Drivers

| ID | Criterion |
|---|---|
| AC-D1 | Creating a driver with a valid `name` returns `201` and a generated `id`. |
| AC-D2 | Creating with missing or invalid `name` returns `422`. |
| AC-D3 | Getting by existing `id` returns `200`. |
| AC-D4 | Getting by non-existent or malformed id follows AC-A5 / AC-A6. |
| AC-D5 | Listing without filters returns all drivers in insertion order. |
| AC-D6 | Listing with `name` applies exact, case-insensitive match. |
| AC-D7 | Updating with a valid `name` returns `200`. |
| AC-D8 | Deleting a driver with no usages returns `204`. |
| AC-D9 | Deleting a driver referenced by any usage returns `409`. |

### Usages

| ID | Criterion |
|---|---|
| AC-U1 | Starting a usage with existing automobile and driver, valid `startDate` and `reason`, when neither has an active usage, returns `201` with `endDate: null`. |
| AC-U2 | Starting when the automobile already has an active usage returns `409` (`AUTOMOBILE_IN_USE`). |
| AC-U3 | Starting when the driver already has an active usage returns `409` (`DRIVER_IN_USE`). |
| AC-U4 | When both automobile and driver are busy, the automobile conflict is reported first. |
| AC-U5 | Starting with a non-existent automobile or driver id returns `404`. |
| AC-U6 | Starting with invalid payload returns `422`. |
| AC-U7 | Finishing an active usage with `endDate >= startDate` returns `200` and sets `endDate`. |
| AC-U8 | Finishing an already finished usage returns `409` (`USAGE_ALREADY_FINISHED`). |
| AC-U9 | Finishing a non-existent usage returns `404`. |
| AC-U10 | After finishing, the same automobile and driver may start a new usage. |
| AC-U11 | Listing returns all usages (active and finished) with nested current `driver` and `automobile` data. |
| AC-U12 | Finished usages remain in the list (history preserved). |
| AC-U13 | Concurrent start attempts for the same automobile or driver within one process: exactly one succeeds; the other receives `409`. |

### Cross-cutting

| ID | Criterion |
|---|---|
| AC-X1 | `GET /health` returns `200` and `{ "status": "ok" }`. |
| AC-X2 | Unknown routes return `404`. |
| AC-X3 | Malformed JSON body returns `400`. |
| AC-X4 | Unexpected errors return `500` without leaking stack traces. |

## 4. Business rules (frozen hypotheses)

1. An automobile cannot have more than one active usage (`endDate === null`).
2. A driver cannot have more than one active usage.
3. An active usage is defined solely by `endDate === null`.
4. Start is rejected when automobile or driver is already in an active usage.
5. Finish is allowed only for active usages.
6. Missing resources produce HTTP `404` (valid UUID) or `422` (malformed UUID).
7. Inputs are validated for required fields and datetime format.
8. Plate uniqueness after trim + uppercase (enforced in the domain service, not only at the HTTP boundary). Driver names are trimmed in the domain service.
9. Future `startDate` is allowed and already occupies automobile and driver.
10. No overlap checks among finished usages.
11. Deletion blocked if any usage references the entity.
12. Usage list joins live related data (no snapshot).
13. Mutual exclusion for start/finish/delete integrity is process-local only.

## 5. Out of scope

Authentication, pagination, CORS configuration beyond defaults, databases, queues, microservices, Mercosul plate formats, usage update (`PUT`), soft deletes.
